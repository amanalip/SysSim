# Metrics semantics

SysSim reports synthetic model output, not production telemetry. Every metric belongs to one of the scopes below so that totals, rates, and distributions are not mistaken for one another.

## Metric scopes

- **Lifetime counters** accumulate from the most recent simulation reset: offered, accepted, completed, succeeded, failed, and dropped requests.
- **Latest interval rates** count events in the newest populated one-second simulation-time bucket: offered, accepted, completed, and dropped QPS. `currentQps` remains a compatibility alias for completed throughput, not configured load.
- **Recent latency distributions** use the bounded recent-completion buffer (currently at most 1,000 requests). Successful and failed request latency averages are reported separately. Percentiles include successful completions only.
- **Component throughput** is a lifetime average (`component requests / elapsed simulation seconds`). The UI labels it accordingly.

An offered request is generated by the traffic model. An accepted request enters traversal. A completed request reaches a terminal result after acceptance. A dropped request may be rejected before acceptance because a safety bound is reached, or may complete with a dropped result. Consequently, offered, accepted, completed, and dropped are intentionally separate dimensions.

## Percentiles

Latency percentiles use the nearest-rank definition on ascending values:

`quantile(p) = sorted[ceil(p × n) - 1]`

The index is clamped for empty, zero-probability, and full-probability inputs. This makes small samples predictable: for `[10, 20]`, p50 is `10` and p95 is `20`.

## Latency breakdown

Each completed request exposes queue wait, component service, network, and total end-to-end time. The engine preserves this invariant, subject only to display rounding:

`queue wait + service time + network time = total end-to-end latency`

Queue wait records modeled waits such as app-server queues, database connection queues, rate-limiter queues, proxy backpressure, and serverless queues. Service time is time spent at components. Network time is the remaining modeled edge-transfer latency.

## Capacity and utilization

Capacity checks share one canonical calculation. `maxThroughputQps` is per replica for component types with a `replicas` setting, so effective capacity is `maxThroughputQps × replicas`; otherwise it is `maxThroughputQps`. Generic utilization and bottleneck detection use that same effective capacity. Component-specific models may expose a more precise utilization value, which takes precedence.

Cache hits and misses come from the cache model's counters. Database active connections come from the database model. Queue depth is the live post-drain model value, rather than a cumulative request count.
